1. Executive Summary

The GNSS AI Translation Engine is a purpose-built software system that automatically translates the technical content of Precision-GNSS.com from English into European Spanish, with an architecture prepared to extend to French, German, Italian and Portuguese. Unlike a generic machine-translation plug-in, it is designed specifically for technical GNSS/RTK/surveying content, where a mistranslated number, unit, or qualifier can change the factual meaning of a claim.

The system does not translate blindly. Every piece of content passes through three independent, specialised AI calls — a Translator, a Technical Reviewer, and a Terminology Validator — plus a deterministic local check against a curated domain glossary, before a translation is considered safe for human review. This report summarises what has been built, how it works, what technology it uses, and what it costs to run against real DeepSeek pricing, validated with real API calls and real content scraped from the live site.

Current state: the core translation engine (extraction-agnostic: Translator, Reviewer, Terminology Validator, Glossary Engine, long-content chunking) is fully implemented, covered by 60 automated tests, and has been validated against the real DeepSeek API on real precision-gnss.com content. The WordPress/WPML integration layer is designed and documented but not yet implemented, pending access to a staging copy of the site.

2. What the Tool Does

The engine sits between WordPress (running WPML and Elementor) and the DeepSeek AI API, acting as an independent, auditable layer — never a simple script that dumps text into an AI model and republishes whatever comes back. Its responsibilities are:

  • Extract translatable content from WordPress pages while explicitly protecting URLs, email addresses, SKUs, model numbers, shortcodes, and API keys from being altered.
  • Translate that content with strict technical-fidelity rules — preserving exact meaning, numbers, units, conditions, warnings, and degree of certainty.
  • Review every translation independently for semantic drift: information added, removed, or altered compared to the source.
  • Validate terminology against a mandatory domain glossary (GNSS, RTK, PPK, surveying, geodesy terms), both via a second AI call and a free, deterministic local check.
  • Score and gate every translation before it is ever published — translations are created as drafts pending human approval, never auto-published.
  • Track and reuse translations via a translation memory, so only content that actually changed gets re-translated.

4. Architecture

The system deliberately keeps three concerns apart: WordPress never talks to DeepSeek directly, and DeepSeek never has any awareness of WordPress. A thin, well-defined engine sits in between and owns all the intelligence — extraction rules, glossary logic, quality gates, and audit logging.

The gnss-bridge component exists because WPML does not expose a public REST API for creating or linking translations — that operation is only supported through internal PHP hooks (wpml_set_element_language_details and related filters) that must run inside WordPress itself. A minimal, auditable bridge plugin is the safest way to reach those hooks from an external Python service, without ever writing directly to WPML's database tables — which WPML's own documentation explicitly advises against.

5. Core Logic: the Translation Pipeline

Translation and quality assurance are deliberately split into independent AI calls rather than one combined request. This is not a stylistic choice — it directly reflects a validated real-world finding: during testing, the Translator alone produced a subtle but real technical error (translating "achieves a fix within 5 seconds" — i.e. in at most 5 seconds — as "en menos de 5 segundos", i.e. in strictly less than 5 seconds). The independent Reviewer call caught this exact error and correctly failed the translation. A single combined call would very likely have missed it.

5.1 Translator

A single DeepSeek call, constrained by a strict system prompt with 15 mandatory rules (preserve exact meaning, numbers, units, conditions, warnings, certainty; never simplify, invent, or drop technical information) and 6 explicit prohibitions (never soften or strengthen claims, never translate protected product names or acronyms without instruction). The model is forced into JSON mode and must return a structured object: translation text, a 0-1 confidence score, a list of flagged issues, and the glossary terms it actually used.

5.2 Technical Reviewer

A second, independent DeepSeek call that receives both the source and the translation and checks specifically for information added, removed, or altered; changed conditions, certainty, or terminology. Returns a strict pass/fail plus a list of issues — this is the call that caught the "within 5 seconds" error described above.

5.3 Terminology Validator

A third, independent DeepSeek call auditing the translation against the mandatory glossary terms relevant to that content, flagging any deviation from the required target term.

5.4 Glossary Engine

Domain terminology (GNSS, RTK, PPK, surveying, geodesy) is stored in JSON files and only the subset of terms actually present in the current text is sent to DeepSeek on each call — never the whole glossary — keeping prompts small and costs down. A free, local, deterministic check (validate_translation()) also flags obviously missing mandatory terms without spending any API budget.

5.5 Chunking

Long content (a full article, a long product page) is split at paragraph boundaries — falling back to sentence boundaries only for a single oversized paragraph — so numbers, units, and technical terms are never cut mid-word. Each chunk is translated with the same shared context and glossary, then rejoined.
